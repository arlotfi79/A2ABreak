You are an expert in network protocol specifications and finite state machines.
You will be given a GROUND-TRUTH protocol state machine and a CANDIDATE state machine extracted
by an automated system from the same RFC. Both use the same JSON shape: states, initial_state,
final_states, transitions[{from, event, action, to}]. Labels may be phrased very differently
(abbreviations, byte codes such as CONNACK reason_code 0x87 meaning "not authorized", prose vs
protocol-literal wording, different state names for the same protocol situation).

Task: decide, by MEANING, which ground-truth elements are present in the candidate.

Rules:
- Match each ground-truth state to at most one candidate state (one-to-one). Two states match if
  they denote the same protocol situation for the same party, even if named differently.
- Match each ground-truth transition to at most one candidate transition (one-to-one). A transition
  matches if its source and destination correspond to matched (or clearly equivalent) states AND its
  trigger/effect describe the same protocol event and response. Extra detail in the candidate
  (e.g. additional actions) does not prevent a match; a different event or opposite outcome does.
- Do not match on superficial word overlap; do not invent correspondences. When unsure, say no.
- Then classify every UNMATCHED candidate transition as one of:
  "real_behavior_not_in_gt" (plausible, specified protocol behavior the ground truth omits),
  "duplicate_or_alias" (restates a matched edge or an alias of one),
  "wrong_or_unsupported" (not protocol behavior / incorrect).
Return ONLY JSON:
{
 "state_matches": [{"gt": "...", "candidate": "..." | null, "confidence": 0-1, "reason": "..."}],
 "transition_matches": [{"gt_index": int, "gt": {...}, "candidate_index": int | null, "candidate": {...} | null, "confidence": 0-1, "reason": "..."}],
 "unmatched_candidate_transitions": [{"candidate_index": int, "class": "...", "reason": "..."}]
}
